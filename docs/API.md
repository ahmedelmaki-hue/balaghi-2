# واجهة API المستهدفة — بلاغي

العنوان المحلي المقترح: `http://localhost:5000/api`.

يدخل المواطن بالهاتف وOTP، والموظف الإداري والعامل الميداني باسم مستخدم وكلمة مرور. يحوّل الخادم اسم المستخدم إلى بريد داخلي مرتبط بحساب Supabase Auth؛ لا يُعرض البريد ضمن كائن `user` ولا تُعاد كلمة المرور. قد يظهر البريد عند فك ترميز رمز الوصول، فلا يُعد سرًا. يرسل العميل رمز الوصول إلى Express عبر `Authorization: Bearer <token>`، ويتحقق Express من هوية المستخدم ودوره المخزن على الخادم. دورا `staff` و`field_worker` يعيّنهما المسؤول فقط.

| الطريقة | المسار | الوصول | الوظيفة |
|---|---|---|---|
| POST | `/auth/otp/send` | عام | طلب OTP للرقم `phone` |
| POST | `/auth/otp/verify` | عام | التحقق من `phone` و`code` وإرجاع جلسة المستخدم؛ قد يلزمه إكمال الاسم |
| POST | `/auth/staff/login` | عام | دخول موظف البلدية أو العامل الميداني بـ`username` و`password` وفق دوره المنشأ إداريًا |
| POST | `/auth/refresh` | عام | تجديد جلسة الدخول باستخدام `refresh_token` |
| GET | `/auth/me` | مستخدم | بيانات الحساب الحالي ودوره |
| PATCH | `/auth/me` | مواطن | حفظ `full_name` عند أول دخول؛ لا يقبل تعديل الدور |
| POST | `/reports` | مواطن | إنشاء بلاغ: `image`، `category`، `latitude`، `longitude`، `client_request_id`، و`description`/`address_text` اختياريان. الحد 10 بلاغات جديدة لكل مواطن في اليوم بتوقيت طرابلس؛ ما بعدها يرد بـ429 `daily report limit reached` |
| GET | `/reports/public?bbox=&status=&category=&cursor=&limit=` | عام | علامات بلاغات المنطقة الظاهرة على الخريطة، على دفعات لا تتجاوز 500، دون صور أو بيانات المُبلّغ |
| GET | `/reports/:id/public` | عام | تفاصيل بلاغ عامة دون بيانات المُبلّغ |
| GET | `/reports/mine?status=&page=&limit=` | مواطن | بلاغات صاحب الجلسة وحده، بما فيها المرفوضة، مع فلتر حالة اختياري وصفحات |
| GET | `/reports/staff?status=&review=&field_review=&completion=&acceptance=&category=&date=&report_id=&sort=&page=&limit=` | موظف | البلاغات وبيانات المُبلّغ اللازمة للمتابعة، مع `accepted_at` و`work_started_at` واسم العامل المستلم `assigned_worker_name` و`assigned_worker_username`؛ `acceptance=pending` يعيد البلاغات المعتمدة الجديدة التي لم يستلمها أي عامل بعد؛ `completion=pending` يعيد طلبات الإنجاز المنتظرة، ويمكن البحث والتصفية والترتيب مع الصفحات. يعتمد `date` على تاريخ الملاحظة أو إرسال الإنجاز في قائمتيهما، وعلى تاريخ تقديم البلاغ في غيرهما |
| GET | `/reports/staff/map?bbox=&category=&cursor=&limit=` | موظف | علامات البلاغات في نطاق الخريطة، بما فيها المنتظرة للمراجعة، دون المرفوضة أو بيانات المُبلّغ؛ الحد الأقصى 500 في الصفحة |
| GET | `/reports/field/assigned?view=active&page=&limit=` | عامل ميداني | البلاغات النشطة غير المستلمة لجهة العامل أو التي استلمها بنفسه. يُستبعد منها البلاغ الذي تنتظر ملاحظته الميدانية قرار الموظف حتى يقرر، لذلك تكون `field_issue_pending` في هذه القائمة `false` دائمًا. يضم كل بلاغ `completion_pending` عند انتظار طلب الإنجاز، و`completion_return_note` عند إعادة آخر طلب إنجاز للعمل. `view=resolved` يعيد البلاغات المنتهية التي استلمها العامل بنفسه فقط، دون بيانات المُبلّغ |
| GET | `/reports/field/verifications?page=&limit=` | عامل ميداني | طلبات التحقق قبل الاعتماد لجهته، غير المستلمة أو المستلمة بحسابه فقط، دون بيانات المُبلّغ |
| GET | `/reports/:id/staff` | موظف | تفاصيل البلاغ وبيانات المُبلّغ وسجل الحالات والتحقق والملاحظات وطلبات الإنجاز وقراراتها |
| PATCH | `/reports/:id/verification/request` | موظف | طلب تحقق قبل النشر مع `note` إلزامية؛ يوجّه الخادم الطلب إلى جهة العمل الموافقة للتصنيف |
| PATCH | `/reports/:id/verification/claim` | عامل من الجهة المختصة | استلام مهمة التحقق بحسابه؛ لا يحول البلاغ إلى مهمة إصلاح |
| PATCH | `/reports/:id/verification/respond` | العامل المستلم للتحقق | إرسال `result`: `exists` أو `wrong_location` أو `not_found` أو `unable`، مع `note` إلزامية |
| PATCH | `/reports/:id/verification/cancel` | موظف | إلغاء طلب تحقق مفتوح مع `note` إلزامية إذا تعذّر انتظار الرد |
| PATCH | `/reports/:id/verification/location` | موظف | تصحيح `latitude` و`longitude` بعد نتيجة `wrong_location` وقبل اعتماد البلاغ؛ يرد الخادم بـ422 إذا كان الموقع الجديد خارج نطاق طرابلس المركز |
| PATCH | `/reports/:id/category` | موظف | تصحيح تصنيف بلاغ غير معتمد قبل النشر؛ يُمنع أثناء طلب تحقق مفتوح |
| PATCH | `/reports/:id/approve` | موظف | اعتماد بلاغ جديد ونشره وإسناده تلقائيًا إلى جهة العمل حسب تصنيفه؛ يُمنع أثناء طلب تحقق مفتوح |
| PATCH | `/reports/:id/accept` | عامل من الجهة المسندة | استلام البلاغ بحسابه؛ أول عامل يستلمه يصبح المسؤول عنه، مع بقائه بحالة «جديد» |
| PATCH | `/reports/:id/start` | العامل المسند إليه | تأكيد بدء العمل بعد الاستلام، وتغيير الحالة إلى «قيد المعالجة» مع سجل الحالة |
| POST | `/reports/:id/field-issue` | العامل المسند إليه | رفع ملاحظة ميدانية بسبب `reason` وملاحظة `note` دون صورة؛ الأسباب: `not_found`, `wrong_location`, `duplicate`, `inaccessible`, `other` |
| PATCH | `/reports/:id/field-issue/review` | موظف | حسم الملاحظة بـ`decision`: `continue`، `correct_location` مع `latitude` و`longitude` داخل نطاق طرابلس المركز (وإلا 422)، أو `reject` مع `note` إلزامية |
| POST | `/reports/:id/completion` | العامل الذي استلم البلاغ وبدأ العمل | `multipart/form-data` بصورة `image` إلزامية ووصف `note` اختياري حتى 500 حرف؛ يمكن إرسال `photo_latitude` و`photo_longitude` و`photo_accuracy_m` معًا عند توفر موقع الجهاز؛ تبقى الحالة `in_progress` |
| PATCH | `/reports/:id/completion/review` | موظف | `decision=confirmed` لتأكيد الحل وتغيير الحالة إلى `resolved`، أو `decision=returned` مع `note` إلزامية لإعادته للعمل |
| PATCH | `/reports/:id/release` | موظف | إعادة بلاغ معتمد استلمه عامل (جديد أو قيد المعالجة) إلى قائمة جهته مع `reason` إلزامي: يُفك عن العامل، وتعود حالة «قيد المعالجة» إلى «جديد» مع سجل في تاريخ الحالات. يُرفض بـ409 أثناء طلب إنجاز أو ملاحظة ميدانية معلّقين |
| PATCH | `/reports/:id/status` | موظف | تغيير الحالة وفق القواعد أدناه وتسجيل السبب والموظف في عملية واحدة |
| GET | `/stats/overview` | موظف | العدد الإجمالي والأعداد حسب الحالة والتصنيف، و`pending_review` و`pending_field_review` و`pending_completion` للقوائم التي تنتظر قرار الموظف |
| POST | `/auth/password` | موظف أو عامل أو مسؤول | تغيير كلمة المرور بـ`current_password` و`new_password` (10 إلى 72 حرفًا، مختلفة عن الحالية). يعمل حتى مع `must_change_password`، ويُنهي الجلسات الأخرى ويعيد جلسة جديدة؛ خطأ الكلمة الحالية يُرد بـ400 `current password incorrect` |
| GET | `/admin/users?role=&status=&search=&page=&limit=` | مسؤول بصلاحية إدارة فئة | الحسابات من الفئات التي يملك إدارتها فقط (الرئيسي يرى المسؤولين أيضًا)، مع الحالة و`must_change_password` و`password_changed_at` و`is_owner` و`admin_permissions`، دون البريد الداخلي |
| POST | `/admin/users` | حسب الدور | إنشاء حساب بـ`full_name` و`username` و`role` و`agency` للعامل فقط. الموظف يتطلب `manage_staff`، والعامل `manage_workers`، والمسؤول الرئيسيَّ مع `admin_permissions` اختيارية من `manage_staff` و`manage_workers` و`manage_citizens` و`view_audit`. يعيد `temporary_password` مرة واحدة |
| PATCH | `/admin/users/:id` | حسب الدور | تعديل `full_name` أو `role` أو `agency`، و`admin_permissions` لمسؤول عادي (للرئيسي فقط). لا يغيّر أحد دوره أو صلاحياته، وحساب الرئيسي يُرد بـ409 `owner accounts are managed on the server`. تغيير دور العامل أو جهته يعيد بلاغاته غير المبدوءة إلى قائمة الجهة، ويُرفض بـ409 إذا كان لديه بلاغ قيد المعالجة |
| PATCH | `/admin/users/:id/status` | حسب الدور | `active` مع `reason` اختياري عند التعطيل؛ لا يعطّل أحد نفسه، ولا يُعطَّل الرئيسي من اللوحة. تعطيل العامل يعيد بلاغاته غير المبدوءة ويذكر عدد بلاغاته قيد المعالجة في `released` |
| POST | `/admin/users/:id/reset-password` | حسب الدور | كلمة مؤقتة جديدة تُعاد مرة واحدة، ويُلزَم صاحب الحساب بتغييرها؛ ليست لحساب المنفّذ نفسه. حسابات المسؤولين للرئيسي، والرئيسي يعيد تعيين كلمة رئيسي آخر |
| GET | `/admin/citizens?status=&search=&page=&limit=` | `manage_citizens` | المواطنون مع الهاتف وعدد البلاغات والحالة؛ البحث بالاسم أو الهاتف بالصيغة المحلية |
| PATCH | `/admin/citizens/:id/status` | `manage_citizens` | إيقاف مواطن بـ`active=false` و`reason` إلزامي، أو إعادة تفعيله |
| GET | `/admin/audit?action=&page=&limit=` | `view_audit` | سجل الإجراءات الإدارية مع المنفّذ والحساب المستهدف والتفاصيل |

## الأدوار والحسابات

- مسارات «موظف» أعلاه تقبل المسؤول `admin` أيضًا. مسارات «عامل ميداني» للعامل وحده، فلا يرسل المسؤول إنجازًا ثم يؤكده. مسارات `/admin` للمسؤول وتتطلب الصلاحية المذكورة؛ المسؤول الرئيسي (`is_owner`) يملكها كلها، ويرد الخادم بـ403 `forbidden` لمن لا يملكها.
- صفة المسؤول الرئيسي تُمنح بسكربت الخادم فقط، ولا تُعدَّل أو تُزال عبر API.
- يرفض الخادم كل طلب من حساب معطّل بـ403 `account disabled`، بما فيه طلب رمز OTP للمواطن الموقوف وتجديد الجلسة.
- ما دام `must_change_password` صحيحًا، يرفض الخادم كل المسارات المحمية بـ403 `password change required` إلا `GET /auth/me` و`POST /auth/password`. يعيد الدخول وتجديد الجلسة هذه القيمة ضمن `user`.
- **تحديد معدّل المحاولات:** يرد الخادم بـ429 `too many attempts` مع ترويسة `Retry-After` عند تجاوز: طلب OTP (5 لكل رقم و30 لكل عنوان IP في 15 دقيقة)، التحقق من OTP (10 لكل رقم و60 لكل عنوان)، دخول اللوحة (8 لكل اسم مستخدم و50 لكل عنوان)، وتغيير كلمة المرور (5 لكل حساب). العدّاد في ذاكرة عملية الخادم الواحدة.
- الحسابات لا تُحذف بل تُعطَّل. كل إجراء إداري وكل تغيير لكلمة المرور يُسجَّل في `admin_audit_log`.

## حدود البيانات

- يبدأ البلاغ بحالة `new` مع `approved_at=null`، ولا يظهر للعامة حتى يعتمده موظف عبر `/reports/:id/approve`. يمكن للموظف تصحيح التصنيف قبل الاعتماد؛ عند الاعتماد يُنشر البلاغ ويُسند تلقائيًا إلى جهة العمل حسب تصنيفه. يمكن لصاحبه والموظفين رؤيته أثناء المراجعة. الاعتماد خطوة ظهور مستقلة عن حالات البلاغ العامة الثلاث: جديد، قيد المعالجة، تم الحل. يمكن رفض البلاغ قبل الاعتماد مع سبب، ولا يمكن بدء المعالجة قبل الاعتماد.
- طلب التحقق قبل الاعتماد داخلي واختياري؛ يظل البلاغ غير منشور، ولا يتغير عرض المواطن «بانتظار المراجعة». يستلم الطلب عامل واحد من الجهة المطابقة لتصنيف البلاغ ويرسل النتيجة للموظف. لا يتخذ العامل قرار الاعتماد أو الرفض. أثناء وجود طلب مفتوح لا يمكن اعتماد البلاغ أو رفضه حتى يرد الفريق أو يلغي الموظف الطلب مع سبب. إذا كانت النتيجة `wrong_location` يلزم أن يصحح الموظف الإحداثيات قبل الاعتماد، مع تسجيل التصحيح في سجل التحقق.
- رد قائمة الخريطة يحتوي `id`, `category`, `latitude`, `longitude`, `status`, `created_at` فقط. عند فتح علامة، يجلب العميل التفاصيل العامة من `/reports/:id/public`، وهي `id`, `category`, `description`, `image_url`, `latitude`, `longitude`, `address_text`, `status`, `created_at`. لا يعاد `user_id` أو اسم المواطن أو هاتفه. البلاغ غير المعتمد أو المرفوض لا يعاد في القائمة العامة، وتفاصيله العامة غير متاحة.
- «بلاغاتي» يعيد بلاغات صاحب الجلسة وفق معرفه على الخادم، ولا يعتمد على `user_id` يرسله العميل. يعرض سبب الرفض لصاحب البلاغ.
- الملاحظة الميدانية حالة داخلية وليست حالة عامة رابعة. أثناء تعليقها يُخفى البلاغ من القائمة والخريطة العامة ويُوقف بدء العمل وتغييرات الحالة المعتادة، بينما يظل ظاهرًا لصاحبه وللموظف. بعد قرار الموظف يعود للظهور أو يُرفض مع سبب محفوظ.
- طلب تأكيد الإنجاز حالة داخلية أيضًا. يلتقط العامل صورة بعد الإصلاح من كاميرا صفحة العمل؛ يتحقق الخادم منها، يزيل بياناتها الوصفية، ويحفظها في التخزين الخاص. يسجل وقت الإرسال على الخادم وإحداثيات الجهاز ودقتها إن سمح المتصفح بتحديد الموقع؛ غياب الموقع لا يمنع الإرسال ويظهر للموظف بوضوح. يرى الموظف صورتي البلاغ والإصلاح، ثم يؤكد الحل أو يعيده للعمل مع سبب. تبقى الحالة العامة `in_progress` حتى التأكيد، ويمكن للعامل إعادة إرسال صورة جديدة بعد استكمال العمل. تحفظ الطلبات والقرارات جميعها؛ روابط صور الإنجاز متاحة للموظف فقط ضمن تفاصيل البلاغ.
- رد الموظف قد يضيف `reporter_name` و`reporter_phone` بعد التحقق من دور الموظف.
- بيانات `/auth/me` وجلسات الدخول لا تعرض البريد الداخلي للموظف، ولا توجد نقطة عامة لإنشاء موظف أو تغيير صلاحياته. كلمة المرور لا تحفظ في `profiles`.
- تصنيف البلاغ يقبل فقط `pothole`, `water_leak`, `garbage`.
- لا يقبل الخادم إنشاء بلاغ قبل أن يحفظ المواطن اسمه عبر `/auth/me`.
- الصورة تُفحص وتُرفع عبر الخادم إلى حاوية خاصة في Supabase Storage. يحفظ البلاغ مسارها في التخزين؛ يولّد الخادم `image_url` كرابط عرض مؤقت بعد فحص صلاحية العرض. قد يبقى الرابط الصادر قبل رفض البلاغ قابلًا للاستخدام حتى انتهاء مدته القصيرة. لا يقبل إنشاء بلاغ دون صورة وموقع.
- يعاد استخدام `client_request_id` نفسه عند تكرار محاولة إرسال بلاغ محفوظ محليًا. لا تنشئ المحاولة الثانية بلاغًا مكررًا، ولا تُحسب من الحد اليومي.
- يُحسب الحد اليومي (10) من كل البلاغات التي أرسلها المواطن منذ منتصف ليل طرابلس، والمرفوضة منها أيضًا. يُفحص قبل رفع الصورة، ثم مرة أخرى داخل معاملة تُقفل على المواطن حتى لا يتجاوزه طلبان متزامنان.
- يبدأ `page` من 1، والقيمة الافتراضية لـ`limit` في «بلاغاتي» وقائمة الموظف هي 25، والحد الأعلى 100. الرد يحوي `items`, `page`, `total`, `total_pages`. الترتيب الافتراضي من الأحدث إلى الأقدم مع `id` لحسم تساوي الأوقات؛ يمكن لقائمة الموظف طلب `sort=oldest`.
- `bbox` حدود المنطقة الظاهرة بالترتيب `west,south,east,north`. تُعاد نتائج الخريطة في `items` ومعها `next_cursor` إذا بقيت بلاغات في النطاق؛ القيمة الافتراضية والحد الأعلى للدفعة 500. ينتقل العميل إلى الدفعة التالية عند الحاجة ويجمع النقاط المتقاربة بصريًا.
- بيانات الخريطة تُجلب عند فتحها أو العودة إليها أو تغيير نطاقها، ويمكن تحديثها بالسحب. التحديث الفوري خارج النسخة الأولى.

## انتقالات الحالات

- من `new` إلى `in_progress` فقط بتأكيد العامل المسند إليه بعد الاستلام؛ يستطيع موظف البلدية رفضه.
- من `in_progress` إلى `resolved` فقط عند تأكيد الموظف طلب إنجاز أرسله العامل المسند إليه. يمكن للموظف رفض البلاغ بسبب موثق ما لم يكن طلب الإنجاز معلقًا.
- `resolved` و`rejected` نهائيتان في النسخة الأولى، ولا يقبل تكرار الحالة نفسها.
- الاعتماد متاح فقط للبلاغ الجديد غير المعتمد. إذا تقرر رفضه، يستخدم الموظف انتقال الحالة إلى `rejected` مع السبب.
- يرسل الموظف `status` و`reason` عند الرفض، والسبب إلزامي وغير فارغ. يحفظ في سجل الحالات ويظهر لصاحب البلاغ والموظفين فقط.
- يُحدّث البلاغ ويضاف سجل الحالة في معاملة قاعدة بيانات واحدة؛ إذا فشلت أي خطوة لا يُحفظ التغيير.
- الإسناد والاستلام بيانات داخلية لا تظهر للمواطن كحالات إضافية؛ تبقى الحالات العامة الثلاث كما هي. لا يستطيع العامل عرض بيانات المواطن أو بلاغات عمال آخرين أو فتح إجراءات المراجعة.
- متابعة البلاغ أو تصحيح موقعه بعد ملاحظة ميدانية يبقيان العامل وحالة البلاغ كما هما. الرفض ينهي البلاغ مع سبب يظهر لصاحبه.
- لا يقبل مسار تغيير الحالة العام تحويل البلاغ مباشرة إلى `resolved`؛ قرار التأكيد يتم عبر `/reports/:id/completion/review` ضمن معاملة واحدة مع تسجيله في سجل الحالات.
