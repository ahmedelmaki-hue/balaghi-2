# الشاشات المقترحة لبلاغي

## تطبيق المواطن — Flutter

1. **الترحيب عند الفتح الأول:** أربع صفحات بالرسوم والنصوص والأزرار المعتمدة في [تصميم الترحيب](onboarding.md). يمكن تخطيها؛ تنتهي بالخريطة العامة دون طلب الدخول. لا تظهر في الفتح التالي.
2. **الخريطة الرئيسية:** متاحة دون تسجيل دخول. علامات البلاغات: أحمر للجديد، أزرق لقيد المعالجة، أخضر للمحلول. فلتر للتصنيفات الثلاثة وزر تحديث. زر «بلاغ جديد» يفتح الدخول إن كان المستخدم زائرًا.
3. **الدخول:** إدخال رقم الهاتف ← طلب OTP ← إدخال الرمز. عند أول دخول تظهر شاشة قصيرة للاسم واللقب. لا يُطلب البريد أو كلمة المرور من المواطن.
4. **إنشاء بلاغ:** صورة من الكاميرا أو المعرض ← موقع GPS أو تحديد يدوي على الخريطة ← اختيار واحد من: حفر الطرق، تسرب المياه، تراكم القمامة، مع وصف اختياري ← تأكيد الإرسال. عند انقطاع الاتصال تظهر حالة «بانتظار الإرسال» ويحتفظ التطبيق بالطلب لإعادة المحاولة.
5. **بلاغاتي:** بلاغات المستخدم وحده، 25 بلاغًا في الصفحة، مع زر للصفحة التالية وحالة انتظار الإرسال محليًا إن وجدت. يظهر سبب الرفض إذا رُفض البلاغ. سحب للتحديث.
6. **تفاصيل بلاغ عام:** صورة وتصنيف ووصف وموقع وحالة وتاريخ فقط، دون اسم أو هاتف صاحب البلاغ.

## لوحة البلدية — React

1. **دخول الموظف:** حقل اسم المستخدم وحقل كلمة المرور وزر «دخول». تُفتح اللوحة بعد التحقق من الحساب وصلاحية `staff` الممنوحة إداريًا. لا يظهر البريد الداخلي المستخدم في Supabase Auth.
2. **الملخص:** إجمالي البلاغات وأعداد حسب الحالة والتصنيف، وأحدث البلاغات.
3. **البلاغات:** جدول من 25 بلاغًا في الصفحة مع التنقل بين الصفحات، وخريطة Leaflet تطلب البلاغات في نطاق العرض. فلاتر الحالة والتصنيف والتاريخ. بيانات التواصل تظهر للموظف فقط. زر لتحديث البيانات.
4. **تفاصيل البلاغ:** الصورة والموقع والوصف وبيانات المُبلّغ وسجل تغير الحالات. يمكن نقل الجديد إلى قيد المعالجة أو الرفض، وقيد المعالجة إلى الحل أو الرفض. يتطلب الرفض كتابة سبب. الحالات المحلولة والمرفوضة لا تتغير في النسخة الأولى.

الشاشات هنا وصف أولي؛ يمكن رسم خمس شاشات أساسية للمواطن وثلاث أو أربع للويب حسب متطلبات فصل التصميم.
